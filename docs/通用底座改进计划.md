# 通用底座改进计划

## 文档边界

本文管理 `llm-wiki-agent-release` 通用包的后续改进。目标知识库的数据修复、学科迁移和错题整理另见该知识库自己的改进计划。

| 责任 | 唯一所有者 |
| --- | --- |
| Agent 入口、对话启动门、Git 工作约定 | `AGENTS.md` |
| Wiki 核心合同、三类工作流、知识读写边界 | `WIKI.md` |
| 项目主题、学科、路径、命名和项目偏好 | `PROJECT.md` |
| 可复用的详细操作步骤 | `.agents/skills/` 中已有 skill |
| 考试学习初始化约定 | `scenarios/exam-study/` |
| 人类使用说明和页面模板 | `docs/` |

## 目标架构

通用底座保持四层：

1. **对话启动门**：所有对话一开始都先定位活动知识工作区根目录，并完整读取该根目录的 `WIKI.md` 和 `PROJECT.md`，然后才规划、搜索、回答、委派或写入。编程、调试、普通问答、恢复已有对话和新委派对话使用同一启动门。首次进入该根目录或根目录变化时，再完整读取 `AGENTS.md`。
2. **精简核心合同**：`WIKI.md` 只保留所有对话共同需要的稳定规则和工作流路由；可按需执行的详细步骤由已有 skill 维护。精简后的 `WIKI.md` 仍在所有对话一开始完整读取。
3. **可审查升级**：Git 工作区以已审阅的基线提交和试验分支作为主要升级证据；初始化和升级脚本承担包文件同步、明确退役文件收敛及最小覆盖保护。
4. **结构审计与内容迁移分离**：通用工具只报告错题路径、编号、碰撞、索引和链接事实；具体题目答案、证据和归属由目标知识库决定并验证。

## 实施一：收敛启动合同与 Skill 路由

### 保留在 `WIKI.md` 的核心

- 目录与规范所有者。
- `Add Knowledge`、`Use Knowledge`、`Maintain Wiki` 路由。
- 本地知识优先和来源追踪链。
- 普通问答默认只读、明确记录请求才进入写入流程的边界。
- 原始来源、命名、项目语言和 frontmatter 的稳定约束。
- 新建项目专属学科、分类、路径或命名前先读取并按需更新 `PROJECT.md` 的确认门。
- `wiki/index.md`、`wiki/home.md`、`logs/wiki.md` 的职责和最小完成条件。

### 收敛 `AGENTS.md` 与 `WIKI.md` 的重复

当前两份入口合同没有发现直接冲突，但 `AGENTS.md` 重复展开了 Markdown 与 frontmatter、intake 命名、来源处理、三类工作流、日志及首页和索引更新条件。这些规则已经由 `WIKI.md` 或对应 skill 持有；双份规范会增加修改遗漏和后续语义漂移的风险，也与“一项规则只有一个所有者”的目标不一致。

保留以下必要重复：

- `AGENTS.md` 规定进入知识工作区后必须先完整读取活动根目录的 `WIKI.md` 与 `PROJECT.md`；`WIKI.md` 保留一句自包含的对话启动要求。
- `AGENTS.md` 用简短入口语句声明知识工作由 `WIKI.md` 路由，并明确 `WIKI.md` 是稳定 Wiki 操作合同。
- 只有在规则必须先于规范所有者的读取生效，或涉及写入授权、秘密信息等不可延后边界时，才允许跨文件保留一句保护性摘要；摘要必须指向唯一所有者，不得展开第二套流程。

收敛以下重复正文：

- `AGENTS.md` 的 `Wiki Markdown and Frontmatter`、`Intake Output Names`、`Source Extraction Providers` 和 `Large Sources` 不再复述字段格式、路径算法、provider 细节或例外规则，只保留到 `WIKI.md`、`PROJECT.md` 和本地 skill 的入口。
- `AGENTS.md` 的 `Workflow Router` 只保留何时进入 Wiki 路由及其唯一所有者，不再重复三类工作流的完整触发条件、审查写入规则和流程分支。
- `AGENTS.md` 的 `Wiki Agent Behavior` 不再重复 `logs/wiki.md`、`wiki/index.md` 和 `wiki/home.md` 的更新条件；这些条件只由 `WIKI.md` 持有。
- 人类文档可以解释同一概念，但不得成为额外的规范所有者；示例和摘要应链接回对应合同或 skill。

### 迁入已有 Skill 的详细步骤

| 内容 | 目标所有者 |

### 实施步骤

1. 以现有 `AGENTS.md` 与 `WIKI.md` 为输入建立“规则、唯一所有者、触发条件、是否必须跨文件提前生效”清单，逐条确认必要重复、核心合同与详细操作的归属。
2. 先把详细步骤原意迁入上表中的现有 skill 或 reference，并补齐必要的入口链接；随后从 `WIKI.md` 删除重复的操作正文，只保留稳定不变量、触发条件、停止条件和完成条件。
3. 收缩 `AGENTS.md` 中已经由 `WIKI.md`、`PROJECT.md` 或 skill 持有的详细复述，保留启动守卫、规范所有者和最短路由入口，不通过改写形成新的兼容说明或第二套摘要合同。
4. 同步 `README*`、`docs/usage*` 和合同审查 skill 的入口表述，统一为“所有对话一开始完整读取活动根目录的 `WIKI.md` 与 `PROJECT.md`”，并让详细流程只指向其唯一所有者。
5. 扩充合同测试，检查启动门、唯一所有者、三类路由、写入边界、skill 路由和新学科确认门没有漂移；检查被删除的重复段落没有在其他入口文件重新出现。
6. 对迁移涉及的已有 skill 运行结构校验，并对 `AGENTS.md` 与 `WIKI.md` 做逐条所有权和规则保全复核。

### 验收

- 所有对话的入口合同都要求一开始完整读取 `WIKI.md` 和 `PROJECT.md`，且顺序早于实际工作。
- `AGENTS.md` 与 `WIKI.md` 的跨文件重复仅限启动守卫、最短路由提示和必须提前生效的保护性摘要；每处摘要都能指向唯一规范所有者。
- Markdown、来源命名、provider、来源生命周期、工作流分支及导航投影的详细规则不再同时由 `AGENTS.md` 和 `WIKI.md` 维护。
- `WIKI.md` 中每条保留规则都属于共同核心合同；每个详细流程只有一个已有 skill 或文档所有者。
- 原有来源生命周期、写入边界、追踪性、日志和完成条件没有因精简而丢失。
- 静态测试可证明合同一致；宿主提供可观察轨迹时，再补一项真实启动顺序检查，不增加第二套入口机制。

## 实施二：升级基线与最小覆盖保护

### Git 工作区的标准升级路径

1. 停止目标库的其他写入者，检查当前分支、已跟踪修改、未跟踪文件、忽略文件和敏感文件边界，并逐项确认包管理路径上的本地定制是保留、迁移还是由包版本替换。
2. 用户确认准确的基线提交范围、基准分支和最终集成位置后，在任务分支形成基线提交 `A`。
3. 在该任务分支运行一次升级，形成只包含升级结果的提交 `B`。
4. 审查 `A..B`、包管理路径、`.gitignore` 结果和受保护的忽略文件，并运行对应测试。
5. 将已经验证的任务分支精确集成到记录的基准分支；集成后重跑检查，升级脚本不再重复执行。

Git 的提交、分支和集成始终由操作者在明确授权后执行，升级脚本本身不写 Git 历史。

### 脚本内的最小保护

`scripts/init.ps1`、`scripts/init.sh`、`scripts/upgrade.ps1` 和 `scripts/upgrade.sh` 共用以下行为合同：

| 目标状态 | 行为 |
| --- | --- |
| 包管理文件缺失 | 创建 |
| 源文件与目标文件逐字节相同 | 跳过 |
| Git 中的包管理目标路径有已跟踪修改、暂存修改或内容不同的同名未跟踪文件 | 在首次写入前停止并打印冲突路径 |
| Git 中的包管理目标路径干净且内容不同 | 覆盖为包版本 |
| manifest 明确列出的退役包文件已跟踪且干净 | 移除 |
| 退役文件路径已修改、未跟踪或缺少 Git 基线 | 在首次写入前停止并打印冲突路径 |
| 非 Git 目标中已有同名且内容不同的文件 | 在首次写入前停止并打印冲突路径 |
| 目标根的既有祖先、目标根或待写路径包含符号链接、目录联接或 reparse point | 在首次写入前停止 |
| `PROJECT.md`、`.gitignore`、`.venv` 或固定运行路径的现有类型不符 | 在首次写入前停止 |

表中的内容比较只适用于 `scripts/upgrade-manifest.txt` 展开的包管理文件；目录项只展开 `scripts/package-files.txt` 中明确记录的已跟踪包文件，未跟踪本地文件不进入发布包。退役规则也只作用于 manifest 明确列出的旧包路径，其他目标专有文件继续保留。`PROJECT.md` 与 `.gitignore` 不使用该覆盖规则：前者保留，后者沿用目标域策略合并语义；两者与 `.venv`、固定运行结构仍参加同一次路径结构预检。运行知识数据不进入包文件内容冲突判断。脚本输出人可读的创建、跳过、替换、移除和冲突摘要，Git 提交差异是升级前后的规范对比证据。

### 实施落点

| 文件 | 改动 |
| --- | --- |
| 四个 init/upgrade 脚本 | 在任何复制、目录补齐或 `uv sync` 前完成包管理路径和固定运行路径预检 |
| `scripts/package-files.txt` | 固定 manifest 目录项允许发布的已跟踪文件，阻止未跟踪本地文件随目录扫描进入目标 |
| `tests/test_package_scripts.py` | 覆盖缺失、相同、干净替换、明确退役文件、Git 冲突、非 Git 冲突、仅运行数据修改和 `.gitignore` 语义 |
| `docs/usage.md`、`docs/usage.zh-CN.md` | 记录基线提交、任务分支、单次升级、差异审查和精确集成流程 |

### 验收

- 冲突分支在第一次写入前退出，目标文件树保持不变。
- 仅运行知识页为脏时，不影响包管理路径检查。
- Git 试验分支上的升级只运行一次，最终集成的是已测试提交。
- PowerShell 与 Bash 对上述状态给出相同结果。

## 实施三：普通跨平台 CI

Bash 支持纳入日常包测试，不再作为独立架构阶段或目标知识库升级的前置项。

### 实施步骤

1. 在现有 package test workflow 中增加 `ubuntu-latest` job；仓库尚无该 workflow 时创建一个最小 workflow。
2. 运行 `bash -n scripts/init.sh scripts/upgrade.sh`。
3. 通过 `uv run --no-project` 执行标准库合同测试，避免为脚本合同同步完整 provider 依赖；Linux 跑真实 Bash fixture，Windows 跑真实 PowerShell fixture。

### 验收

日常 CI 同时验证 PowerShell 和 Bash 路径；目标知识库只依赖已经发布并通过常规检查的包版本。

## 实施四：考试错题结构审计

### 责任边界

新增一个只检查源内容、只写显式报告文件的 CLI，负责以下结构事实：

- 文件名是否匹配 `<NNN>-<knowledge-topic>.md`；
- 科目内三位序号是否重复；
- 建议目标路径是否碰撞；
- 学科错题索引是否缺项、重项或指向错误目标；
- 当前错题页的入站 wikilink，以及学科索引中的解析状态。

题目答案、证据可靠性、循环证据、正式错题资格和主主题归属由目标知识库逐页检查，并保存在批次验收记录中；语义正确性与正式资格保留给用户确认。

### 实施落点

| 文件 | 改动 |
| --- | --- |
| `.agents/skills/obsidian-wiki-lint/scripts/lint_wiki.py` | 保持现有实现；审计 CLI 直接复用其代码屏蔽、wikilink 提取和目标解析函数 |
| `scenarios/exam-study/scripts/audit_wrong_questions.py` | 新增按 vault 与规范科目运行的结构审计；除显式报告外不写 vault，不增加中间抽象层 |

审计记录包含当前路径、解析状态、候选序号、主题、建议目标路径、索引条目和错题页入站链接；重复序号、目标碰撞和索引未解析项独立汇总。数组按规范化相对路径和行号排序。无发现返回 0，有待迁移或待判断项返回 1，参数或根目录错误返回 2。

## 实施五：来源摄入质量门禁与链接闭环

### 目标与边界

本阶段阻止空提取、导航占位、空分块、过度碎片化、不可复验的尺寸理由和特殊字符断链进入 `intake/processed/`。它只维护可机械验证的评审面、分块结构、尺寸状态和链接语法，不自动判断两个块在语义上是否应该合并，不产品化交接包中的临时 chunker、迁移器或模糊 repair 脚本，也不使用交接报告中的 151、147、256 等未复算数量驱动批量写入。

责任保持单一：

| 责任 | 所有者 |
| --- | --- |
| canonical `source.md`、Source Review Gate、薄 manifest、最终路径 lint 顺序 | `intake-lifecycle.md` |
| 分块路径、五列 index、2000/10000 阈值、尺寸例外与诊断 | `large-source-chunking.md`、`audit_chunks.py` |
| 空白、placeholder、navigation stub、无可评审文本与稀疏提示 | `audit_intake_file.py` |
| 例外登记的原子写入 | `record_chunk_exception.py` |
| Wikilink 扫描、lint 与受限修复 | `obsidian-wiki-lint` |
| Source Card 精确模板占位检查与语义质量 | 标准 lint、`wiki-quality-review` |

### 行为合同

1. `source.md` 是 Source Review Gate 接受的 canonical Markdown extraction。普通抽取和 provider 分片保留完整抽取文本；只有既有 Excerpt-Type 合同允许受约束摘录。分块、索引、晋升和重建不覆盖、截断或重排它。
2. 内容单位统一为 `utf8-normalized-ceil-div3-v1`：仅去掉开头 BOM、统一换行后按 UTF-8 字节数除以 3 向上取整。`audit_intake_file --json` 总是输出 schema 2；空白、已知 stub、已知 placeholder、无可评审文本是 hard error，稀疏和大源是 warning，表格、代码和数学计入正文。
3. 非空 leaf 的软下限为 2000，硬上限为 10000。每个 `<2000` 块都 warning；脚本不判断相邻合并或语义边界。`>10000` 块 hard fail。空块 hard fail 且不可例外。
4. 每级 index 使用五列：`块 | 标题与覆盖范围 | 内容说明 | 规模与尺寸裁决 | 内容评审`。尺寸单元格使用确定文法；单块标题必须可描述内容，多标题、fallback 或标题不足时必须填写内容说明和稳定 locator。整源 ingest 状态不进入块表。
5. 可见理由只在最近 index 行。根 `chunks/index.md` 的唯一 HTML 注释 registry 只保存全局 policy，以及每个例外的相对路径、kind、完整内容哈希、完整理由哈希和评审引用。有效接受进入 `accepted_exceptions`，不重复报警；内容、路径、kind、理由、min、max 或算法改变后按原始 under/over 级别重新报警。当前已正常的登记为 obsolete warning；malformed、duplicate、orphan 和 registry/table 分叉为 hard error。
6. 审计器只读。评审者先填写 `accepted-under/over — 理由` 并标记 `reviewed`，再运行 `record_chunk_exception.py`。该命令校验当前块和表行，以同目录临时文件加原子替换更新 registry；重复执行零 diff。旧自由文本理由只报告迁移候选，不静默接受。
7. `audit_chunks` 使用 schema 2 和 `thresholds/errors/warnings/accepted_exceptions/summary`；exit 0 表示无 hard error，1 表示 hard error，2 表示参数、路径或 UTF-8 输入不可读，不增加 `--strict`。
8. `obsidian_links.py` 是唯一带 span 的 Wikilink 扫描器，以 `]]` 闭合。真实 Obsidian 探针已确认单个原样 `]` 可用于 target、alias 和 heading；写成 `\]` 会 unresolved。lint、fixer 和下游审计复用该扫描器。
9. `fix_truncated_links.py` 默认 dry-run，只在显式 target 目录内修复唯一 filename-prefix 截断，保留 `.md`、fragment、alias 和表格转义；不自动删除空格、不做全半角、Unicode、大小写或跨目录 suffix 模糊匹配。写入使用原子替换并可幂等复验。
10. manifest 只保存可重放来源、provider、输出、review 与结果链接；chunk mapping、摘要、caveat 正文和时间线各留在自己的 owner。Source Card 静态层只拒绝模板中的精确占位句，内容是否来源特定、证据是否可定位仍由 `wiki-quality-review` 判断。

### 迁移与验收

- 单个来源先在 sibling staging 中构建 derived chunks 并通过 chunk audit，再只切换 chunk tree；`source.md` 不参与替换。到达最终 `intake/processed/` 路径后运行 focused lint，解决最终相对路径上的断链再 ingest。同一来源单写者，不同来源可并行，shared log 与导航投影串行。
- 存量目标库先只读重扫并重新计算真实数量。旧 index 和理由明确报 migration candidate；不保留永久 legacy 分支。先修唯一、可证明的断链，再逐来源重建和复验。
- 回归矩阵覆盖空 source/tree/index/leaf、source 与 leaf 的 image-only、table/code/math、1999/2000/10000/10001 边界、accepted/stale/obsolete、内容/理由/阈值变化、root-only 与 fenced registry、malformed/duplicate/orphan、BOM/CRLF、index 漂移、特殊字符链接、alias/fragment 保留、dry-run、原子写入和二次运行零 diff。
- 提交前运行 source-extraction、obsidian-wiki-lint、下游 exam audit、来源合同和质量合同测试；再由 AGY Flash、OpenCode Ox、OpenCode GLM 对实现差异与测试证据复核。

## 实施顺序

1. 先完成启动合同与 skill 路由收敛。
2. 完成升级最小保护，供目标知识库建立试验分支后对齐包版本。
3. 完成来源摄入质量门禁与共享 Wikilink 扫描器，再重扫或修复任何目标知识库的 processed 来源。
4. 完成错题结构审计，再进入任何存量错题迁移。
5. 跨平台检查随同上述脚本和测试进入日常 CI，不形成额外交付阶段。

## 规模控制

长期新增实现限定为一个错题结构审计 CLI、一个尺寸例外登记 CLI、一个共享 Wikilink scanner、对应测试和一项双系统常规 CI。链接语义直接复用共享 scanner，升级对比复用 Git，初始化直接调用升级实现。尺寸例外继续在同一 chunk index 内维护，不增加第二张表或独立状态文件。目标库迁移执行器放在批次 `tmp/` 中并在验收后清理。详细操作继续进入已有 skill，不新增通用迁移平台或第二套知识持久化面。

## 运行重量复核

| 路径 | 实际加载与执行 | 控制结果 |
| --- | --- | --- |
| 对话启动 | 完整读取约 160 行的 `WIKI.md` 和项目自己的 `PROJECT.md` | 共同合同保持短小，具体 skill 按请求加载 |
| 普通问答与编程 | 本地范围定位后直接处理 | 不运行来源摄入、全库审查或外部评审；Markdown 写入只 lint 最小受影响范围 |
| 来源摄入 | 读取 intake lifecycle、source kind 和已选 provider 用法 | provider 选项在当前来源真正需要时确认；registry、contract、setup、PDF preflight 和 chunk 细则按条件读取 |
| 结构检查 | 全库健康检查先跑标准 lint；窄范围业务审计复用同一解析语义 | 聚焦审计不承担无关的全库检查 |
| Obsidian 辅助 skill | 只提供请求所需的格式或实时应用操作 | 内容读写继续由 `WIKI.md` 路由 |
| Skill 验证 | 结构校验和代表性检查为默认路径 | 独立 Agent 或外部评审按用户要求、歧义和影响范围决定 |
| 初始化与升级 | 两个 init 是薄 wrapper；PowerShell 与 Bash 各自在调用 `uv` 前完成冲突门；manifest 只清理明确退役且干净的旧包文件 | 保留启动边界所需的双平台实现，不增加 dry-run 协议、配置 schema 或 Git 自动化 |
| CI | Windows 与 Ubuntu 各跑同一组标准库合同测试；Ubuntu 另做 Bash 语法检查 | 不为合同测试同步完整 provider 依赖 |
| 错题治理 | 一个结构审计 CLI 输出确定性 JSON，且只写显式报告 | 内容判断和迁移写入留给知识库批次，不形成通用迁移平台 |

## 完成定义

1. 所有对话一开始都经过单一、可测试的 `WIKI.md` 与 `PROJECT.md` 完整读取门。
2. `WIKI.md` 只保留共同核心合同，详细步骤全部路由到现有所有者且无规则缺失。
3. 包升级由 Git 基线和已测试提交提供对比证据，脚本能在写入前阻止包管理路径冲突。
4. Bash 行为由常规 CI 覆盖。
5. 错题结构审计只负责可机械判断的结构事实，并能为目标库迁移提供稳定输入。
6. canonical source 不再被 chunking 覆盖；空提取、空 chunk tree 和空 leaf 均 hard fail。
7. `<2000` 块持续 warning，只有与当前内容、理由、路径和 policy 完全匹配的 Source Review Gate 例外才能静音；变化后会重新提示。
8. processed 链接由同一个经过真实 Obsidian 探针验证的 scanner 检查，受限修复保持原始文件名、fragment 和 alias，且二次执行零 diff。
