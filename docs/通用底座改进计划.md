# 通用底座改进计划

## 文档边界

本文管理 `llm-wiki-agent-release` 通用包的后续改进。目标知识库的数据修复、学科迁移和错题整理另见该知识库自己的改进计划。

| 责任 | 唯一所有者 |
| --- | --- |
| Agent 入口、对话启动门、Git 工作约定 | `AGENTS.md` |
| Wiki 核心合同、三类工作流、知识读写边界 | `WIKI.md` |
| 项目主题、学科、路径、命名、活动场景和项目偏好 | `PROJECT.md` |
| 可复用的详细操作步骤 | `.agents/skills/` 中已有 skill |
| 考试学习初始化约定和专属工作法 | `scenarios/exam-study/` |
| 人类使用说明和页面模板 | `docs/` |

## 目标架构

通用底座保持四层：

1. **对话启动门**：所有对话一开始都先定位活动知识工作区根目录，并完整读取该根目录的 `WIKI.md` 和 `PROJECT.md`，然后才规划、搜索、回答、委派或写入。编程、调试、普通问答、恢复已有对话和新委派对话使用同一启动门。首次进入该根目录或根目录变化时，再完整读取 `AGENTS.md`。
2. **精简核心合同**：`WIKI.md` 只保留所有对话共同需要的稳定规则和工作流路由；可按需执行的详细步骤由已有 skill 维护。精简后的 `WIKI.md` 仍在所有对话一开始完整读取。
3. **所有权升级**：初始化和升级只比较目标中的旧包所有权清单与当前包的新所有权清单；包拥有的核心可替换，项目数据和清单外文件保留，不依赖目标目录的 Git 状态。
4. **结构审计与内容迁移分离**：通用工具只报告错题路径、编号、碰撞、索引和链接事实；具体题目答案、证据和归属由目标知识库决定并验证。
5. **场景按项目激活**：场景的技能只保存在 `scenarios/<name>/skills/`。`PROJECT.md` 记录唯一活动场景；只有该场景已激活且当前任务相关时才读取对应技能，不把场景技能复制到通用 `.agents/skills/`。

## 实施一：收敛启动合同与 Skill 路由

### 保留在 `WIKI.md` 的核心

- 目录与规范所有者。
- `Add Knowledge`、`Use Knowledge`、`Maintain Wiki` 路由。
- 本地知识优先和来源追踪链。
- 普通问答默认只读、明确记录请求才进入写入流程的边界。
- 原始来源、命名、项目语言和 frontmatter 的稳定约束。
- 新建项目专属学科、分类、路径或命名前先读取并按需更新 `PROJECT.md` 的确认门。
- `wiki/index.md`、`wiki/home.md`、`logs/wiki.md` 的职责和最小完成条件。

### 收敛 `AGENTS.md` 与 `WIKI.md` 的重复

当前两份入口合同没有发现直接冲突，但 `AGENTS.md` 重复展开了 Markdown 与 frontmatter、intake 命名、来源处理、三类工作流、日志及首页和索引更新条件。这些规则已经由 `WIKI.md` 或对应 skill 持有；双份规范会增加修改遗漏和后续语义漂移的风险，也与“一项规则只有一个所有者”的目标不一致。

保留以下必要重复：

- `AGENTS.md` 规定进入知识工作区后必须先完整读取活动根目录的 `WIKI.md` 与 `PROJECT.md`；`WIKI.md` 保留一句自包含的对话启动要求。
- `AGENTS.md` 用简短入口语句声明知识工作由 `WIKI.md` 路由，并明确 `WIKI.md` 是稳定 Wiki 操作合同。
- 只有在规则必须先于规范所有者的读取生效，或涉及写入授权、秘密信息等不可延后边界时，才允许跨文件保留一句保护性摘要；摘要必须指向唯一所有者，不得展开第二套流程。

收敛以下重复正文：

- `AGENTS.md` 的 `Wiki Markdown and Frontmatter`、`Intake Output Names`、`Source Extraction Providers` 和 `Large Sources` 不再复述字段格式、路径算法、provider 细节或例外规则，只保留到 `WIKI.md`、`PROJECT.md` 和本地 skill 的入口。
- `AGENTS.md` 的 `Workflow Router` 只保留何时进入 Wiki 路由及其唯一所有者，不再重复三类工作流的完整触发条件、审查写入规则和流程分支。
- `AGENTS.md` 的 `Wiki Agent Behavior` 不再重复 `logs/wiki.md`、`wiki/index.md` 和 `wiki/home.md` 的更新条件；这些条件只由 `WIKI.md` 持有。
- 人类文档可以解释同一概念，但不得成为额外的规范所有者；示例和摘要应链接回对应合同或 skill。

### 实施步骤

1. 以现有 `AGENTS.md` 与 `WIKI.md` 为输入建立“规则、唯一所有者、触发条件、是否必须跨文件提前生效”清单，逐条确认必要重复、核心合同与详细操作的归属。
2. 先把详细步骤原意迁入上表中的现有 skill 或 reference，并补齐必要的入口链接；随后从 `WIKI.md` 删除重复的操作正文，只保留稳定不变量、触发条件、停止条件和完成条件。
3. 收缩 `AGENTS.md` 中已经由 `WIKI.md`、`PROJECT.md` 或 skill 持有的详细复述，保留启动守卫、规范所有者和最短路由入口，不通过改写形成新的兼容说明或第二套摘要合同。
4. 同步 `README*`、`docs/usage*` 和合同审查 skill 的入口表述，统一为“所有对话一开始完整读取活动根目录的 `WIKI.md` 与 `PROJECT.md`”，并让详细流程只指向其唯一所有者。
5. 扩充合同测试，检查启动门、唯一所有者、三类路由、写入边界、skill 路由和新学科确认门没有漂移；检查被删除的重复段落没有在其他入口文件重新出现。
6. 对迁移涉及的已有 skill 运行结构校验，并对 `AGENTS.md` 与 `WIKI.md` 做逐条所有权和规则保全复核。

### 验收

- 所有对话的入口合同都要求一开始完整读取 `WIKI.md` 和 `PROJECT.md`，且顺序早于实际工作。
- `AGENTS.md` 与 `WIKI.md` 的跨文件重复仅限启动守卫、最短路由提示和必须提前生效的保护性摘要；每处摘要都能指向唯一规范所有者。
- Markdown、来源命名、provider、来源生命周期、工作流分支及导航投影的详细规则不再同时由 `AGENTS.md` 和 `WIKI.md` 维护。
- `WIKI.md` 中每条保留规则都属于共同核心合同；每个详细流程只有一个已有 skill 或文档所有者。
- 原有来源生命周期、写入边界、追踪性、日志和完成条件没有因精简而丢失。
- 静态测试可证明合同一致；宿主提供可观察轨迹时，再补一项真实启动顺序检查，不增加第二套入口机制。

## 实施二：基于新旧清单的包所有权升级

### 唯一责任源

升级脚本在写入前读取两组包元数据：

- **旧所有权**：目标目录现存的 `scripts/upgrade-manifest.txt` 与 `scripts/package-files.txt`；
- **新所有权**：当前包中的同名两份文件。

当前 manifest 必须在所有权条目前唯一声明 `inventory all`；完整 inventory 必须带 `# inventory-format: complete` 机器标记。inventory 以 `active <path>` 或 `remove <path>` 完整列出 manifest 中每个 `file`、每个 `dir` 展开的活动文件和每个 `remove` 路径，是该版本所有权及其分类的最终激活点；manifest 负责声明候选分类，inventory 负责最终激活。新包缺项、孤儿、重复或分类冲突均在写入前阻断。旧目标没有 inventory 格式标记时按早期 directory-only 格式兼容读取；依赖同步成功后先把它原子类型化为同一份旧所有权，再提交新 manifest 和最终 inventory。任一中断窗口都以 typed 旧 inventory 的路径和分类为准，因此新增路径及 `remove`→`active` 等分类切换不会提前生效。

`file` 与由 `dir` 展开的路径构成活动所有权集合，`remove` 是已激活的退役所有权。只有两份旧元数据都不存在时才进入首次接管门；带完整格式标记的 inventory 可单独作为中断检查点，单独 manifest、无标记的单独 inventory、格式错误、重复或路径越界都会阻断升级，不做部分推断。旧清单拥有的目标文件可以缺失，后续状态机负责重建或退役。

### 状态机

| 旧包拥有 | 新包拥有 | 目标现状 | 行为 |
| --- | --- | --- | --- |
| 是 | 是 | 缺失、相同或不同 | 缺失时创建，相同时跳过，不同时替换为新包版本 |
| 否 | 是 | 缺失 | 创建 |
| 否 | 是 | 与新包相同 | 跳过并由新包接管 |
| 否 | 是 | 与新包不同或类型错误 | 新认领路径冲突；首次写入前停止 |
| 是 | 否 | 新 manifest 明确 `remove` | 目标存在时删除，不存在时跳过 |
| 是 | 否 | 新 manifest 未明确 `remove` | 新包清单错误；首次写入前停止，禁止静默遗留或删除 |
| 旧 tombstone | 新包不再声明 | 任意 | 释放退役所有权；保留目标现状 |
| 否 | 否 | 任意 | 目标自有，保留 |

新 manifest 中的 `remove` 只有在旧元数据把同一路径记为 active 或 remove 时才可删除现存文件。首次出现的 `remove` 遇到现存目标文件会冲突并保留；目标缺失时先不动作，只有 manifest 与最终 inventory 都成功提交后才成为已激活 tombstone。这样，manifest 已提交而 inventory 中断后由用户新建的同名文件，重跑仍会冲突而不会被删除。

目标缺少可用旧元数据时进入一次性接管门：缺失的新包路径可以创建，与新包逐字节相同的路径可以接管；已有不同内容的新包路径以及已有的退役路径都报冲突，等待人工明确归属。该门只处理从无所有权元数据的旧分发物进入当前合同，不形成长期兼容分支。

### 共同保护

- PowerShell 与 Bash 都先完成源包完整性、旧/新清单、目标路径、类型、符号链接、`PROJECT.md`、`.gitignore`、`.venv` 和固定运行结构的全量预检，再进行第一次写入；Windows PowerShell 另覆盖目录联接与其他 reparse point。
- `PROJECT.md`、`.env`、运行知识目录和新旧清单都未拥有的目标文件保持原样；已有 `.gitignore` 保留其目标域规则，只补齐密钥与技术缓存规则。
- 依赖同步成功后，旧 path-only inventory 先原子类型化为同一份旧所有权；没有旧元数据的目标先写入只认领新建 inventory 控制文件自身的 typed 检查点。随后先提交新 manifest，最后提交带 `active`/`remove` 分类的最终 inventory。每次都使用同目录临时文件原子替换，因此中断在检查点之后或 manifest 之后，无修改重跑可以完成，而被改动的尚未激活业务路径仍视为冲突。
- `init.ps1` 与 `init.sh` 继续只是升级脚本的薄入口，不增加 `-Scenario` 或另一套复制逻辑。
- 输出稳定的 create、unchanged、replace、remove、conflict 汇总；第二次运行必须零内容差异。

### 实施落点与验收

| 文件 | 改动 |
| --- | --- |
| `scripts/upgrade.ps1`、`scripts/upgrade.sh` | 读取目标旧清单和当前新清单，执行同一所有权状态机 |
| `scripts/init.ps1`、`scripts/init.sh` | 保持薄入口和现有参数，不新增场景参数 |
| `scripts/package-files.txt`、`scripts/upgrade-manifest.txt` | 维护确定的包所有权与明确退役路径，不加入版本号、哈希清单或场景注册表 |
| `tests/test_package_scripts.py` | 覆盖空目标、旧包替换、新增接管、新路径冲突、明确退役、遗漏退役声明、旧元数据缺失、目标自有文件保留、项目数据保留、路径安全、幂等和双平台一致性 |
| `README*`、`docs/usage*`、`AGENTS.md` | 只描述所有权升级的当前行为、项目数据保留和冲突条件 |

验收要求：所有冲突都在第一次目标写入前关闭；PowerShell 与 Bash 对同一 fixture 产生同类结果；合法升级后新包拥有的文件与当前包一致，项目自有内容不变，二次运行零 diff。

## 实施三：普通跨平台 CI

Bash 支持纳入日常包测试，不再作为独立架构阶段或目标知识库升级的前置项。

### 实施步骤

1. 在现有 package test workflow 中覆盖 `windows-latest`、`ubuntu-latest` 与 `macos-latest`。
2. 运行 `bash -n scripts/init.sh scripts/upgrade.sh`。
3. 通过 `uv run --no-project` 执行标准库合同测试，避免为脚本合同同步完整 provider 依赖；Linux 与 macOS 跑真实 Bash fixture，Windows 跑真实 PowerShell fixture。
4. macOS 明确使用系统 `/bin/bash` 执行 Bash 3.2 合同；Windows 上的 Bash 脚本直接拒绝运行并指向 PowerShell。

### 验收

日常 CI 同时验证 PowerShell 和 Bash 路径；目标知识库只依赖已经发布并通过常规检查的包版本。

## 实施四：考试学习场景技能与结构审计

### 场景激活与文件边界

考试学习工作法只维护一份规范正文：

```text
scenarios/exam-study/
├── README.md
├── PROJECT.template.md
├── starter-pages.md
└── skills/exam-study/
    ├── SKILL.md
    ├── references/workflow-contract.md
    └── scripts/audit_wrong_questions.py
```

`README.md` 只负责显式初始化：确认当前起始页需要的项目字段，把 `Active scenario: exam-study` 和其他已确认值写入根 `PROJECT.md`，再按 `starter-pages.md` 创建最小起始页面。它不复制技能，不修改 `AGENTS.md` 或 `WIKI.md`，也不承担日常错题处理步骤。

根 `AGENTS.md` 在对话启动时读取 `PROJECT.md` 后，只在 `Active scenario` 精确匹配某个已分发场景且当前请求与该场景相关时读取 `scenarios/<name>/skills/<name>/SKILL.md`。未激活场景不读取；场景目录存在不代表启用。初始化和升级 CLI 不增加 `-Scenario`，也不增加场景注册表、活动副本、版本号、哈希或独立同步协议。场景源文件随通用包所有权升级，根 `PROJECT.md` 的活动选择始终保留。

### 场景技能责任

`exam-study` 技能拥有正式试题接纳、错题页与错题索引、学习计划以及何时运行结构审计。它把来源材料摄入路由回 `WIKI.md` 与 `source-extraction`，且不得绕过 Source Review Gate、推断用户未确认的错误原因或学科、创建并行队列、修改入口合同，或为普通单题记录强制运行批量审计。

审计 CLI 只检查源内容、只写显式报告文件，负责以下结构事实：

- 文件名是否匹配 `<NNN>-<knowledge-topic>.md`；
- 科目内三位序号是否重复；
- 建议目标路径是否碰撞；
- 学科错题索引是否缺项、重项或指向错误目标；
- 当前错题页的入站 wikilink，以及学科索引中的解析状态。

题目答案、证据可靠性、循环证据、正式错题资格和主主题归属由目标知识库逐页检查，并保存在批次验收记录中；语义正确性与正式资格保留给用户确认。

### 实施落点

| 文件 | 改动 |
| --- | --- |
| `.agents/skills/obsidian-wiki-lint/scripts/lint_wiki.py` | 保持现有实现；审计 CLI 直接复用其代码屏蔽、wikilink 提取和目标解析函数 |
| `scenarios/exam-study/skills/exam-study/scripts/audit_wrong_questions.py` | 按 vault 与规范科目运行结构审计；除显式报告外不写 vault，不增加中间抽象层 |
| `tests/test_exam_wrong_question_audit.py` | 覆盖规范名、历史名、空科目、重复序号、目标碰撞、索引、跨页链接和未解析链接 |
| `scenarios/exam-study/skills/exam-study/SKILL.md` | 日常触发、核心步骤、边界与验证入口 |
| `scenarios/exam-study/skills/exam-study/references/workflow-contract.md` | 正式试题、错题、计划和结构审计的详细工作合同 |
| `scenarios/exam-study/README.md` | 只记录初始化步骤和到场景技能的路由 |

审计记录包含当前路径、解析状态、候选序号、主题、建议目标路径、索引条目和错题页入站链接；重复序号、目标碰撞和索引未解析项独立汇总。数组按规范化相对路径和行号排序。无发现返回 0，有待迁移或待判断项返回 1，参数或根目录错误返回 2。

### 公开命令

```powershell
uv run --no-project python scenarios/exam-study/skills/exam-study/scripts/audit_wrong_questions.py --vault "C:\path\to\workspace" --subject "建设工程经济" --output "C:\path\to\audit.json"
```

### 验收

- 同一 fixture 重复运行产生相同报告，除显式报告文件外源页面与索引不变。
- 审计使用与标准 lint 相同的链接语义。
- 迁移前的结构发现对应退出码 1；目标库完成迁移后的复检对应退出码 0。
- 未激活场景时不加载任何考试学习技能；激活后仅在考试学习相关请求中读取场景内唯一技能。
- 旧 `scenarios/exam-study/scripts/` 路径完全退役，不保留别名、转发器或双路径文档。

## 实施五：来源摄入质量门禁与链接闭环

### 目标与边界

本阶段阻止空提取、导航占位、空分块、过度碎片化、不可复验的尺寸理由和特殊字符断链进入 `intake/processed/`。它只维护可机械验证的评审面、分块结构、尺寸状态和链接语法，不自动判断两个块在语义上是否应该合并，不产品化交接包中的临时 chunker、迁移器或模糊 repair 脚本，也不使用交接报告中的 151、147、256 等未复算数量驱动批量写入。

责任保持单一：

| 责任 | 所有者 |
| --- | --- |
| canonical `source.md`、Source Review Gate、薄 manifest、最终路径 lint 顺序 | `intake-lifecycle.md` |
| 分块路径、五列 index、2000/10000 阈值、尺寸例外与诊断 | `large-source-chunking.md`、`audit_chunks.py` |
| 空白、placeholder、navigation stub、无可评审文本与稀疏提示 | `audit_intake_file.py` |
| 例外登记的原子写入 | `record_chunk_exception.py` |
| Wikilink 扫描、lint 与受限修复 | `obsidian-wiki-lint` |
| Source Card 精确模板占位检查与语义质量 | 标准 lint、`wiki-quality-review` |

### 行为合同

1. `source.md` 是 Source Review Gate 接受的 canonical Markdown extraction。普通抽取和 provider 分片保留完整抽取文本；只有既有 Excerpt-Type 合同允许受约束摘录。分块、索引、晋升和重建不覆盖、截断或重排它。
2. 内容单位统一为 `utf8-normalized-ceil-div3-v1`：仅去掉开头 BOM、统一换行后按 UTF-8 字节数除以 3 向上取整。`audit_intake_file --json` 总是输出 schema 2；空白、已知 stub、已知 placeholder、无可评审文本是 hard error，稀疏和大源是 warning，表格、代码和数学计入正文。
3. 非空 leaf 的软下限为 2000，硬上限为 10000。每个 `<2000` 块都 warning；脚本不判断相邻合并或语义边界。`>10000` 块 hard fail。空块 hard fail 且不可例外。
4. 每级 index 使用五列：`块 | 标题与覆盖范围 | 内容说明 | 规模与尺寸裁决 | 内容评审`。尺寸单元格使用确定文法；单块标题必须可描述内容，多标题、fallback 或标题不足时必须填写内容说明和稳定 locator。整源 ingest 状态不进入块表。
5. 可见理由只在最近 index 行。根 `chunks/index.md` 的唯一 HTML 注释 registry 只保存全局 policy，以及每个例外的相对路径、kind、完整内容哈希、完整理由哈希和评审引用。有效接受进入 `accepted_exceptions`，不重复报警；内容、路径、kind、理由、min、max 或算法改变后按原始 under/over 级别重新报警。当前已正常的登记为 obsolete warning；malformed、duplicate、orphan 和 registry/table 分叉为 hard error。
6. 审计器只读。评审者先填写 `accepted-under/over — 理由` 并标记 `reviewed`，再运行 `record_chunk_exception.py`。该命令校验当前块和表行，以同目录临时文件加原子替换更新 registry；重复执行零 diff。旧自由文本理由只报告迁移候选，不静默接受。
7. `audit_chunks` 使用 schema 2 和 `thresholds/errors/warnings/accepted_exceptions/summary`；exit 0 表示无 hard error，1 表示 hard error，2 表示参数、路径或 UTF-8 输入不可读，不增加 `--strict`。
8. `obsidian_links.py` 是唯一带 span 的 Wikilink 扫描器，以 `]]` 闭合。真实 Obsidian 探针已确认单个原样 `]` 可用于 target、alias 和 heading；写成 `\]` 会 unresolved。lint、fixer 和下游审计复用该扫描器。
9. `fix_truncated_links.py` 默认 dry-run，只在显式 target 目录内修复唯一 filename-prefix 截断，保留 `.md`、fragment、alias 和表格转义；不自动删除空格、不做全半角、Unicode、大小写或跨目录 suffix 模糊匹配。写入使用原子替换并可幂等复验。
10. manifest 只保存可重放来源、provider、输出、review 与结果链接；chunk mapping、摘要、caveat 正文和时间线各留在自己的 owner。Source Card 静态层只拒绝模板中的精确占位句，内容是否来源特定、证据是否可定位仍由 `wiki-quality-review` 判断。

### 迁移与验收

- 单个来源先在 sibling staging 中构建 derived chunks 并通过 chunk audit，再只切换 chunk tree；`source.md` 不参与替换。到达最终 `intake/processed/` 路径后运行 focused lint，解决最终相对路径上的断链再 ingest。同一来源单写者，不同来源可并行，shared log 与导航投影串行。
- 存量目标库先只读重扫并重新计算真实数量。旧 index 和理由明确报 migration candidate；不保留永久 legacy 分支。先修唯一、可证明的断链，再逐来源重建和复验。
- 回归矩阵覆盖空 source/tree/index/leaf、source 与 leaf 的 image-only、table/code/math、1999/2000/10000/10001 边界、accepted/stale/obsolete、内容/理由/阈值变化、root-only 与 fenced registry、malformed/duplicate/orphan、BOM/CRLF、index 漂移、特殊字符链接、alias/fragment 保留、dry-run、原子写入和二次运行零 diff。
- 提交前运行 source-extraction、obsidian-wiki-lint、下游 exam audit、来源合同和质量合同测试；再由 AGY Flash、OpenCode OX、OpenCode GLM、OpenCode Kimi 对实现差异与测试证据复核。

## 实施六：维护反馈技能收口

`.agents/skills/wiki-maintenance-feedback/` 只打包已经由拥有工作流确认的发现与证据，不自行调查、复现、修复、保存、跟踪或外发。技能只能复用拥有工作流已经创建的现有 fixture；没有现成 fixture 时报告 `none`，不得为报告创建或执行 fixture。

专项合同测试同时保证：

- 旧的 `use the smallest synthetic fixture` 指令不存在，新指令明确“只复用既有 fixture、否则 `none`、不创建、不执行”；
- 无 fixture 与有既有 fixture 两条行为路径都遵守该边界；
- `AGENTS.md` 不包含报告内部状态名 `fixed-in-worktree` 或 `fixed-in-commit`，避免入口合同承担报告 schema；
- 修改后重新运行维护反馈专项测试、skill 结构校验和完整合同测试。

## 实施顺序

1. 先完成启动合同与 skill 路由收敛。
2. 完成维护反馈技能收口并单独验证。
3. 完成基于新旧清单的包所有权升级，使分发后的目标库无需版本号或 Git 状态即可升级。
4. 完成考试学习场景技能和活动场景路由，再进入任何存量错题迁移。
5. 来源摄入质量门禁与共享 Wikilink 扫描器作为已落地能力随完整回归复验。
6. 跨平台检查随同上述脚本和测试进入日常 CI，不形成额外交付阶段。

## 规模控制

长期新增实现限定为一个场景内考试学习 skill、一个错题结构审计 CLI、一个尺寸例外登记 CLI、一个共享 Wikilink scanner、对应测试和一项双系统常规 CI。链接语义直接复用共享 scanner；升级只复用新旧包清单，初始化直接调用升级实现。尺寸例外继续在同一 chunk index 内维护，不增加第二张表或独立状态文件。场景技能不复制到通用 skill 目录，不建立注册表或同步层。目标库迁移执行器放在批次 `tmp/` 中并在验收后清理，不新增通用迁移平台或第二套知识持久化面。

## 运行重量复核

| 路径 | 实际加载与执行 | 控制结果 |
| --- | --- | --- |
| 对话启动 | 完整读取约 160 行的 `WIKI.md` 和项目自己的 `PROJECT.md` | 共同合同保持短小，具体 skill 按请求加载 |
| 普通问答与编程 | 本地范围定位后直接处理 | 不运行来源摄入、全库审查或外部评审；Markdown 写入只 lint 最小受影响范围 |
| 来源摄入 | 读取 intake lifecycle、source kind 和已选 provider 用法 | provider 选项在当前来源真正需要时确认；registry、contract、setup、PDF preflight 和 chunk 细则按条件读取 |
| 结构检查 | 全库健康检查先跑标准 lint；窄范围业务审计复用同一解析语义 | 聚焦审计不承担无关的全库检查 |
| Obsidian 辅助 skill | 只提供请求所需的格式或实时应用操作 | 内容读写继续由 `WIKI.md` 路由 |
| Skill 验证 | 结构校验和代表性检查为默认路径 | 独立 Agent 或外部评审按用户要求、歧义和影响范围决定 |
| 初始化与升级 | 两个 init 是薄 wrapper；PowerShell 与 Bash 各自在调用 `uv` 前解析新旧所有权并完成冲突门；manifest 只清理明确退役的包路径 | 不增加 dry-run、版本号、哈希清单、Git 状态判断或场景参数 |

## 完成定义

1. 所有对话一开始都经过单一、可测试的 `WIKI.md` 与 `PROJECT.md` 完整读取门。
2. `WIKI.md` 只保留共同核心合同，详细步骤全部路由到现有所有者且无规则缺失。
3. 包升级只由目标旧清单与当前新清单判定所有权；包拥有的核心可替换，新认领冲突和遗漏退役声明在写入前停止，项目数据保持不变。
4. Bash 行为由常规 CI 覆盖。
5. `PROJECT.md` 是活动场景唯一选择源；考试学习技能只有场景目录中的一份，未激活或任务无关时不加载。
6. 错题结构审计只负责可机械判断的结构事实，并能为目标库迁移提供稳定输入。
7. canonical source 不再被 chunking 覆盖；空提取、空 chunk tree 和空 leaf 均 hard fail。
8. `<2000` 块持续 warning，只有与当前内容、理由、路径和 policy 完全匹配的 Source Review Gate 例外才能静音；变化后会重新提示。
9. processed 链接由同一个经过真实 Obsidian 探针验证的 scanner 检查，受限修复保持原始文件名、fragment 和 alias，且二次执行零 diff。
10. 维护反馈技能只复用已有证据与 fixture；没有 fixture 时明确为 `none`，不创建或执行复现材料。
